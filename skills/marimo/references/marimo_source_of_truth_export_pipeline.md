# Marimo Source-of-Truth Export Pipeline

In Eric's tutorial/documentation repos, the marimo `.py` file is the single
source of truth for a notebook. The `.ipynb` (mkdocs/jupyter) or `.md`
(zensical) versions are BUILD ARTIFACTS: gitignored, never committed alongside
the `.py`, and regenerated at build time by a `marimo export` step prepended to
the docs build task.

Established in two projects:
- **nxviz** (2026-06-02): `.ipynb` → marimo `.py`; `build_docs.py` runs
  `marimo export` to `.md`, then `zensical build`; generated `.md` gitignored.
- **Network-Analysis-Made-Simple** (2026-07-13): "get rid of the ipynb files";
  `.py` is source, `.ipynb` regenerated via `marimo export ipynb` in build-docs.

## Export command surface

```bash
# Run inside the project's pixi env (marimo is a project dep, NOT global):
pixi run marimo export ipynb notebooks/01-intro/01-graphs.py   # -> 01-graphs.ipynb
pixi run marimo export md   notebooks/01-intro/01-graphs.py     # -> 01-graphs.md (zensical path)
```

`marimo` is a project-level dependency (pixi/uv env), not a global CLI — invoke
via `pixi run marimo ...` or `uv run marimo ...`, never bare `marimo`.

## Migration procedure (6 steps)

1. **Verify export works** on one notebook before bulk-migrating:
   `pixi run marimo export ipynb <one>.py` and confirm the output is valid.
2. **Untrack ALL generated files**: `git rm --cached **/*.ipynb` (or `*.md`).
   Include `archive/` and `scripts/`/utility notebooks that have NO `.py`
   counterpart — the user's directive is "untrack ALL of them", not "only the
   paired ones". Files stay on disk; only git tracking is removed.
3. **Add the pattern to `.gitignore`**: `*.ipynb` (and/or `*.md`), with a
   comment that these are generated by `marimo export` in the build task.
4. **Create an export script** (e.g. `scripts/export_notebooks.py`) that:
   - finds marimo `.py` notebooks by scanning for the `import marimo` app
     header (NOT every `.py` — the repo has non-notebook `.py` modules),
   - exports each to the target format in the same directory,
   - is idempotent (safe to run every build).
5. **Wire export into the build task**: prepend the export step to
   `build-docs` (and `serve-docs`) in `[tool.pixi.feature.docs.tasks]` so the
   chain is `export_notebooks && mkdocs build` (or `... && zensical build`).
6. **Update deploy CI** (`deploy.yaml` / GitHub Actions) to run the export step
   before the docs build, then verify the deploy succeeds.

## Gotchas

- **Identify marimo notebooks by content, not extension.** Marimo app `.py`
  files begin with `import marimo` and `__generated_with` / `app = marimo.App()`
  headers. A glob over `**/*.py` will catch library modules (`nams/solutions/`,
  `build_docs.py`) that are NOT notebooks and must not be exported. Scan for the
  marimo header.
- **Untracking is irreversible-ish for unpaired notebooks.** `archive/*.ipynb`
  and `scripts/bookbuilder/*.ipynb` with no `.py` source become untracked and
  gitignored — they vanish from the repo (still on disk locally). This is the
  intended outcome per "get rid of the ipynb files"; do NOT special-case them
  back into tracking.
- **Export must run BEFORE the docs builder.** mkdocs/zensical consume the
  generated `.ipynb`/`.md`; if export is missing from the task, the build
  silently renders stale or missing notebook pages.
- **CI env parity.** The export step runs in CI's pixi env — ensure `marimo` is
  in the `docs` feature deps and the task uses `python -m` / `pixi run`, not
  `uvx` (not available in the CI pixi env — nxviz 06-02).
- **marimo version sensitivity — CycleError vs graceful fallback.** Older
  marimo (e.g. 0.15.2) raises a FATAL `CycleError` on notebooks with complex
  cell-dependency graphs; the export ABORTS with no output file. Newer marimo
  (0.23.14+) degrades gracefully: it prints a non-fatal warning ("using
  top-down order instead of topological") and still produces a valid output.
  In a multi-env pixi project where the `docs` env pins an OLDER marimo than
  the `default` env, run the export task (`export-ipynb`) in the env with the
  NEWER marimo. Diagnostic: if `marimo export ipynb` aborts with `CycleError`
  on a notebook that exports fine elsewhere, check `pixi list marimo` vs
  `pixi list -e docs marimo` — the version skew is the cause. Discovered
  Network-Analysis-Made-Simple 2026-07-14: 03-stats.py CycleError under
  docs-env marimo 0.15.2; resolved by running `export-ipynb` as a default-env
  task (marimo 0.23.14).
- **mkdocs.yml / zensical.toml reference the generated files.** After
  migration, the doc config still points at `*.ipynb` / `*.md` paths — those
  paths must be where the export script writes. Verify the doc builder finds
  the regenerated files.
- **Generated artifacts reappear as Modified (M), not Deleted (D), after `git
  reset`.** During migration commit-splitting, previously-staged-deleted
  `*.ipynb` files can reappear in `git status` as **Modified (M)** instead of
  Deleted (D). Cause: a RUNNING marimo server (file watcher / auto-download) or
  the export script (`pixi run export-ipynb`) REGENERATES the `.ipynb`
  artifacts on disk from the updated `.py` sources while you are still
  mid-commit, so the working tree holds fresh `.ipynb` content differing from
  HEAD old `.ipynb` content -> reads as M. Do NOT spend reasoning turns on
  M-vs-D, and do NOT `git rm` (deletes from disk) or re-stage deletions. The
  goal is to UNTRACK, not delete: run `git rm --cached **/*.ipynb` (step 2 of
  the procedure) — it drops them from the index, leaves the working-tree copy in
  place, and with `*.ipynb` in `.gitignore` they become permanently ignored.
  The regenerated copy stays on disk harmlessly. Discovered
  Network-Analysis-Made-Simple 2026-07-14 commit-splitting after `git reset`
  (3 reasoning turns spent on the M-vs-D puzzle before reaching the `git rm
  --cached` conclusion).

## Distinct from sibling marimo skills

- **marimo-pair**: working INSIDE a running marimo kernel (read/edit cells). Not
  about build pipelines.
- **awesome-marimo-notebook**: crafting engaging notebook CONTENT (narrative,
  widgets, pedagogy). Not about CI/export.
- **THIS skill**: the BUILD/CI layer turning `.py` sources into the docs
  artifact, and the git-tracking discipline that makes `.py` the source of truth.

## Batch export testing gotchas

- **`marimo export` WARNINGS contain the word "error" — do NOT string-match
  for failure.** When a notebook has cell-level issues but can still export,
  marimo prints: `Warning: Notebook has errors, using top-down order instead
  of topological.` The word "errors" here triggers a FALSE-POSITIVE FAIL in a
  batch test that greps output for "Error"/"error". Use the command's EXIT
  CODE (non-zero = failure) and verify the output file exists — a warning
  with a valid output file is a SUCCESS. Discovered Network-Analysis-Made-
  Simple batch export test (2026-07-13): 03-stats.py export succeeded but was
  flagged as failed because the warning text contained "errors".
- **Duplicate `import marimo as mo` cells cause MultipleDefinitionError at
  export time.** If a notebook has two or more cells that each do `import
  marimo as mo` (common when CellTour/wigglystuff cells auto-import `mo`
  inside their function body alongside a standard mo-provider cell), marimo
  raises `MultipleDefinitionError: multiple definitions of the name mo`. The
  standard pattern is: ONE cell does `import marimo as mo` and returns it
  (`return (mo,)`); all other cells receive `mo` as a cell-function parameter
  (`def _(mo):`). Fix by removing the redundant `import marimo as mo` from
  extra cell(s). Adding a new cell with `def _(mo):` to a notebook that
  already has a duplicate-import issue can surface the pre-existing conflict.
  This is the `mo`-specific instance of marimo's single-definition rule.
